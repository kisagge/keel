# apps/web 에디터 — 실행 중에 내린 판단

16개 태스크를 서브에이전트로 돌리는 동안, 계획이 답을 안 주거나 **계획 자체가
틀렸거나** 리뷰와 구현이 갈렸을 때 정한 것들이다. 사람을 기다리느라 멈추는 대신
정하고 적었다.

각 항목 끝의 **틀렸을 때의 값**은 그 판단이 틀렸을 경우 무엇을 잃는지다.
되돌리고 싶은 것이 있으면 거기부터 읽으면 된다.

결론은 코드와 주석에 이미 들어가 있다. 여기 남기는 것은 **왜 그렇게 정했는가**와
**틀렸다면 무엇을 치르는가** — 검사로는 못 지키는 종류라 글로 남기는 것 말고
방법이 없다.

## 사전 스캔

같은 글자를 다시 쓰는 수정을 돌려준다(`planSetNodeKind` 는 `[]` 를 돌려준다).
그대로 두면 계획의 검사가 지고, 무엇보다 같은 글자 다시 쓰기는 되돌리기 역사에
빈 칸을 남기고 남의 화면에 쓸데없는 갱신을 보낸다 — 계획이 막겠다고 적어 둔 바로
그것이다. `editText` 가 `insert` 와 현재 구간의 글자가 같은 수정을 버리게 한다.
— 틀렸을 때의 값: 수정마다 문자열 비교 한 번이 늘어난다. 동작 위험은 없다.

**3.** `React.RefObject`·`React.CSSProperties` 처럼 **React 이름공간을 import

import 하지 않으므로 모듈 안에서 UMD 전역을 쓰면 타입 검사가 깨진다. — 틀렸을 때의

패키지 전부에 번지므로 앱에서만 덮어쓴다.
— 틀렸을 때의 값: 앱의 타입 해석이 라이브러리들과 달라진다. `nodenext` 가 더
엄격한 쪽이라 앱에서 통과한 것이 라이브러리에서 깨질 일은 없고, 반대로 앱에서만
확장자 규칙이 빡빡해질 수는 있다. 실제로 typecheck·lint·test·build 가 전부
통과하는 것을 확인했다.

**7.** **`transpilePackages` 를 안 쓴다.** 계획과 스펙이 "이걸 빼면 워크스페이스

진짜 관문인 `moduleResolution` 을 대상으로 바꿨다.
— 틀렸을 때의 값: 나중에 어떤 패키지가 Turbopack 이 못 읽는 꼴을 내놓으면 그때
다시 넣어야 한다. 그때는 진짜 이유를 주석에 적을 수 있다.

일이 없도록, 이 변경도 태스크 리뷰의 diff 에 그대로 들어간다.
— 틀렸을 때의 값: 없다. 리뷰가 받는 diff 는 어느 쪽이 썼든 같다.

**9.** **고치지 않는다. 커밋된 대로 둔다** — 리뷰의 실패 모드가 재현되지 않고,
제안한 수정은 실제 해를 끼친다. 직접 확인한 것 둘:
 (1) `apps/web/.next` 와 tsbuildinfo 를 지우고 `pnpm typecheck --force` → 통과.
     부수 효과만 있는 import 는 `noUncheckedSideEffectImports` 를 켜야 못 찾는
     것을 문제 삼는데 이 저장소는 안 켜 두었다. 리뷰가 추론만 하고 안 돌려 봤다.

틀린 것은 구현이 아니라 계획이다 — 브리프가 도구가 관리하는 파일의 글자를
붙들려 한 것이 잘못이었다. 계획 본문을 고쳐 이유를 적었다.
— 틀렸을 때의 값: 나중에 `noUncheckedSideEffectImports` 를 켜면 그때 이 두 줄이
문제가 된다. 그때는 `next-env.d.ts` 를 tsconfig `include` 에서 빼면 된다.

## 최종 전체 리뷰

**36.** 리뷰어를 네 번째로 띄우지 않고 내가 본다. 계획을 쓴 사람이라 새 눈은
아니지만, 이 리뷰가 노리는 것(태스크 사이 합성·중복·공허한 검사·주석의 거짓)은
새 눈보다 **전체를 한 번에 보는 눈**이 필요한 것들이다. 세 번 더 시도하는 값이
얻는 것보다 크다.
— 틀렸을 때의 값: 새 눈만 잡을 부류(이름·구조의 어색함)를 놓친다.
