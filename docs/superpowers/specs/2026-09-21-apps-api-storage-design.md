# apps/api — 저장 설계 (중계 + 영속화)

2026-09-21

## 왜 만드는가

`apps/web` 이 돈다. 그런데 **새로고침하면 작업물이 사라진다.** 문서는
`SEED` 상수에서 매번 새로 서고, 고친 것은 어디에도 남지 않는다. 씨앗 파일의
주석이 그것을 솔직히 적어 두었다 — "저장은 `apps/api` 의 일이라는 것을 화면이
솔직하게 드러낸다."

그래서 지금 배포하면 **새로고침 한 번에 30 분을 잃는 1 인용 에디터**가
공개된다. README 첫 줄은 "텍스트로 관리하는 **실시간 협업** 다이어그램"인데
실시간도 협업도 없다. 이 판이 그 거리를 메운다.

이 판이 끝나면 두 사람이 같은 URL 을 열어 서로 고치는 것을 보고, 탭을 닫았다
다시 열어도 문서가 그대로 있다.

## 이 판의 범위

`apps/api` 는 README 에서 다섯 가지를 한 항목에 묶어 두었다 — Yjs 중계,
Postgres 로그 + R2 스냅샷, 구글 로그인, 프레즌스, 오프라인 재접속. 그것은
독립된 서브시스템 다섯이지 하나가 아니다. 스펙 하나에 담으면 아무것도 못
끝낸다.

**이 판은 첫 조각만 한다 — 중계와 영속화.** 중계가 받은 업데이트를 그대로
로그에 쌓는 구조라 둘은 실제로 분리되지 않는다.

**여기에 브라우저 로컬 저장(`y-indexeddb`) 하나를 더 끌어온다.** 원래 다섯째
조각이지만, 빼고 내보내면 **알면서도 데이터 유실 경로를 배포하는 것**이 된다 —
연결이 끊긴 채 고치다 탭을 닫으면 그 작업이 사라진다. 의존성 하나에 배선 몇
줄이라 값이 작고, 잃는 것이 크다. 오프라인의 나머지(충돌 UX, 백오프 조정, 상세
동기화 상태)는 그대로 미룬다.

나머지는 각자 스펙 → 계획 → 구현 주기를 따로 갖는다. 순서는 인증 →
프레즌스 → 오프라인이 자연스럽다. 프레즌스는 `PaintOptions.selection` 이
`Set<string>` 이라 사람별 색을 못 담는 것부터 고쳐야 한다(README 가 이미 적어
두었다).

## 정해진 것

- **NestJS + Prisma.** `pnpm-workspace.yaml` 의 `allowBuilds` 에 `@nestjs/core`
  와 `prisma` 가 이미 적혀 있다. 그 결정을 따른다.
- **로컬 먼저.** `compose.yaml` 의 Postgres 하나로 돈다. 배포 대상은 이 판의
  범위가 아니다. **R2 스냅샷도 미룬다** — 스냅샷은 Postgres 의 `bytea` 로
  충분하고, 외부 의존을 하나 줄인다.
- **문서는 URL 로 가른다.** `/d/<id>`. 추측하기 어려운 id 가 당분간 접근 권한
  역할을 한다. 인증이 얹힐 때 구조가 안 바뀐다.
- **인스턴스 1 대.** 같은 문서가 두 프로세스 메모리에 뜨면 서로의 업데이트를
  모른다. README 가 Redis 팬아웃을 명시적으로 범위 밖에 두었다.
- **표준 `y-websocket` 프로토콜.** 우리 프로토콜을 만들지 않는다. 클라이언트는
  `WebsocketProvider` 를 꽂기만 하고, 서버는 `@y/websocket-server/utils` 의
  `setupWSConnection` 과 `setPersistence` 를 쓴다.
- **브라우저에도 저장한다.** `y-indexeddb` 를 같은 `Y.Doc` 에 함께 붙인다.
  연결 상태와 무관하게 모든 업데이트가 브라우저에 쌓이고, 다시 붙을 때 CRDT 가
  양쪽을 병합한다.

## 왜 스냅샷만 저장하지 않는가

디바운스로 `Y.encodeStateAsUpdate(doc)` 전체를 주기 저장하는 쪽이 더 짧다.
테이블 하나면 되고 접기 로직도 없다.

그런데 **저장 사이 구간이 통째로 유실된다.** 그리고 버전 히스토리가 안 남아,
README 의 다음다음 일감인 버전 스냅샷 화면을 나중에 처음부터 다시 만들어야
한다. 업데이트 로그는 행 하나를 append 하는 것이라 값이 거의 같은데 잃는 것이
훨씬 적다.

## 데이터 모델

### HTTP 계약

`packages/contract` 가 이 타입들을 들고, web 과 api 가 같은 정의를 본다.

| | 요청 | 응답 |
|---|---|---|
| `POST /d` | 본문 없음 | `201 { id }` — 씨앗이 심긴 새 문서 |
| `GET /d/:id` | — | `200 { id, createdAt, updatedAt }` 또는 `404` |
| `DELETE /d/:id` | — | `204`. 업데이트와 스냅샷은 `onDelete: Cascade` 가 함께 지운다 |

**`DELETE` 는 계획을 쓰다 들어왔다.** 유령 문서 처리를 검사하려면 유령을
만들 수 있어야 하는데, 문서를 지우는 길이 없으면 그 상황을 만들 방법이
없다. 검사 전용 통로를 뚫느니 진짜 기능으로 넣는다 — 어차피 필요하다.

인증이 없는 판이라 **id 를 아는 사람이 지울 수 있다.** id 가 곧 권한인
구조의 대가이고, 인증이 얹힐 때 여기에 소유자 검사가 붙는다.

`GET` 은 **존재 확인이 목적**이라 문서 내용을 담지 않는다. 내용은 ws 로만
오간다. 두 통로가 같은 것을 내면 어느 쪽이 진짜인지 묻는 자리가 생긴다.

**이 `GET` 은 보기보다 무겁게 쓰인다.** 로컬 저장이 붙으면서, 이 응답이
브라우저에 남은 사본을 지울지 말지를 가른다 — `404` 면 지우고 `503` 이면
지키지 않는다(오류 처리 절을 볼 것). `404` 와 `503` 을 뭉개면 서버가 잠깐
아픈 사이에 사람의 오프라인 작업을 우리가 없앤다.

**id 는 21 자 URL-safe 무작위 문자열**(`nanoid` 기본값과 같은 엔트로피)이다.
이것이 당분간 유일한 접근 통제이므로 순번이나 UUIDv4 대신 짧고 추측 어려운
쪽을 쓴다.

```prisma
model Document {
  id        String      @id              // 21 자 URL-safe 무작위 문자열
  createdAt DateTime    @default(now())
  updatedAt DateTime    @updatedAt
  updates   DocUpdate[]
  snapshot  Snapshot?
}

model DocUpdate {
  seq        BigInt   @id @default(autoincrement())
  documentId String
  update     Bytes                        // Yjs 이진 업데이트 그대로
  createdAt  DateTime @default(now())
  document   Document @relation(fields: [documentId], references: [id], onDelete: Cascade)

  @@index([documentId, seq])
}

model Snapshot {
  documentId String   @id
  state      Bytes                        // Y.encodeStateAsUpdate(doc)
  throughSeq BigInt                       // 이 seq 까지를 접은 것이다
  createdAt  DateTime @default(now())
  document   Document @relation(fields: [documentId], references: [id], onDelete: Cascade)
}
```

**바이트로 저장한다.** Yjs 업데이트는 이진이다. base64 텍스트로 바꾸면 33% 더
들고 변환 비용이 매 업데이트마다 붙는다.

**`seq` 가 단조 증가해야 한다.** 재생 순서가 곧 문서다. `createdAt` 으로
정렬하면 같은 밀리초에 들어온 둘의 순서가 불안정하다.

**awareness 는 저장하지 않는다.** 휘발성이고, 저장하면 죽은 커서가 되살아난다.

**`ownerId` 와 `title` 은 넣지 않는다.** 인증은 다음 조각이라 지금 넣으면 채울
값이 없는 열이 된다. 제목은 소스 첫 주석 줄에서 파생할 수 있어 중복 저장할
이유가 없다.

### 복원

`snapshot.state` 를 적용한 뒤 `seq > throughSeq` 인 업데이트를 순서대로 얹는다.
스냅샷이 없으면 처음부터 전부 재생한다.

### 접기

`throughSeq` 이후 행이 **200 개**를 넘으면 접는다.

**순서가 중요하다 — 스냅샷을 먼저 쓰고, 그 다음 접힌 행을 지운다.** 반대로
하면 그 사이에 죽었을 때 문서가 사라진다. 이 순서라면 최악의 경우 중복
적용인데, Yjs 업데이트는 멱등이라 손해가 없다.

**언제 도는가.** 두 자리다.

1. **마지막 클라이언트가 나갈 때**(`writeState`). 아무도 안 보고 있으니 제일
   싼 자리다.
2. **메모리 카운터가 200 을 넘을 때.** 문서마다 append 한 횟수를 세고 있다가
   넘으면 접는다. 이것이 없으면 **아무도 나가지 않는 문서는 영원히 안 접힌다** —
   둘이 하루 종일 붙어 있는 문서가 정확히 그 꼴이고, 그런 문서가 로그가 제일
   길다.

카운터는 메모리에만 있으므로 재시작하면 0 이 된다. 접힐 것이 조금 늦게
접힐 뿐이라 무해하다.

## 서버 구조

```
apps/api/
  prisma/schema.prisma
  src/
    main.ts                   Nest 부트스트랩 + ws 업그레이드 배선
    app.module.ts
    prisma.service.ts
    documents/
      documents.controller.ts POST /d · GET /d/:id
      documents.service.ts    만들기(씨앗 심기)·존재 확인
      seed.ts                 씨앗 텍스트 — 이제 서버가 소유한다
    realtime/
      connection.ts           setupWSConnection 배선과 문지기
      persistence.ts          bindState / writeState
      compaction.ts           접기 판단과 실행
compose.yaml                  Postgres 하나
```

### Nest 의 WebSocket 게이트웨이를 쓰지 않는다

Nest 게이트웨이는 제 어댑터(socket.io 또는 `WsAdapter`)로 메시지를 가로채는데,
`setupWSConnection` 은 생 `ws` 소켓을 받아 **직접 프로토콜을 말한다.**
게이트웨이를 끼우면 그 사이에서 프레임이 한 겹 더 감싸져 프로토콜이 깨진다.

대신 Nest 가 만든 HTTP 서버를 꺼내 `upgrade` 이벤트에
`new WebSocketServer({ noServer: true })` 를 직접 붙인다. Nest 는 HTTP(문서
만들기·조회)와 DI 컨테이너만 맡는다.

### 중계는 문서를 만들지 않는다

upgrade 시점에 `documentId` 가 DB 에 있는지 확인하고, 없으면 **업그레이드
전에** 404 로 끊는다. 확인 자체가 DB 오류로 실패하면 `503` 이다(오류 처리 절을
볼 것).

이게 없으면 URL 오타 하나가 빈 문서를 만들어낸다. 씨앗도 없이 만들어지므로
사용자는 빈 화면을 보고 "저장이 깨졌다" 고 읽는다. 만들기는 `POST /d` 한 곳에만
둔다.

### 문서 수명

`setPersistence` 로 두 갈고리를 건다.

- **`bindState(docName, ydoc)`** — 처음 열릴 때. 스냅샷을 적용하고
  `seq > throughSeq` 를 순서대로 얹은 뒤, `ydoc.on('update')` 를 구독해 들어오는
  업데이트를 `DocUpdate` 행으로 append 한다. 라이브러리 예제는 매 업데이트마다
  전체 상태를 덮어쓰는데, 우리는 증분만 쌓는다.
- **`writeState(docName, ydoc)`** — 마지막 클라이언트가 나갈 때. 남은 쓰기를
  비우고 접기를 검토한다.

### 씨앗은 서버가 한 번만 심는다

`POST /d` 가 서버에서 `Y.Doc` 을 만들고 씨앗을 넣은 뒤
`Y.encodeStateAsUpdate` 를 `DocUpdate` 첫 행으로 저장하고 id 를 돌려준다.

**클라이언트가 각자 심으면 안 된다.** 빈 문서에 두 사람이 동시에 들어오면 양쪽
씨앗이 둘 다 살아남아 문서가 두 배가 된다. 이것은 추측이 아니라 이 저장소가
이미 검사로 증명해 둔 현상이다 — `cb55a9b` 의 "통째로 다시 쓰면 글자가 소멸하는
게 아니라 문서가 둘로 불어난다", `apps/web/test/concurrent.test.ts` 가 `Y.Doc`
둘을 손으로 붙여 확인한 그것이다.

### Yjs GC 는 켜 둔다

y-websocket 문서는 스냅샷이 필요하면 GC 를 끄라고 하지만, 우리 히스토리는
**업데이트 로그**가 들고 있다. 인메모리 GC 는 로그를 건드리지 않으므로 나중에
버전 화면을 만들 때 로그 재생으로 어느 시점이든 복원된다. GC 를 끄면 메모리만
늘어난다.

## apps/web 변경

### 라우팅

```
app/page.tsx          서버 컴포넌트. POST /d 로 문서를 만들고 /d/<id> 로 보낸다
app/d/[id]/page.tsx   지금의 에디터 화면이 그대로 옮겨온다
```

`/` 가 정적 프리렌더에서 빠진다(지금 `○ Static`). 그 대가로 "들어오면 새 문서가
선다" 는 흐름이 서버 한 곳에 모인다.

### 제공자 꽂기

`y-websocket` 과 `y-indexeddb` 를 의존성에 추가하고, **같은 `Y.Doc` 에 둘 다**
붙인다. 방 이름과 IndexedDB 이름은 모두 `[id]`. ws 주소는
`NEXT_PUBLIC_KEEL_WS_URL` 로 받는다.

```js
const local = new IndexeddbPersistence(id, keelDocument.doc);
const remote = new WebsocketProvider(WS_URL, id, keelDocument.doc);
```

`local` 이 있어서 **연결이 끊긴 채 고쳐도 잃지 않는다.** 문제의 성격이
"작업물이 사라진다"(데이터 유실)에서 "아직 남들에게 안 보인다"(가시성 지연)로
바뀐다. 뒤쪽은 표시하면 되는 종류다.

**연결 상태 표시는 여전히 필요하다.** 로컬 저장은 "안 잃는다" 를 참으로 만들
뿐 "공유됐다" 를 참으로 만들지 않는다. 문구는 "지금 고치는 것은 이 브라우저에만
있다" 가 된다.

로컬 저장이 **해결하지 않는 것**: IndexedDB 는 브라우저·출처마다 따로다. 노트북을
닫고 휴대폰에서 여는 경우는 서버에 올라간 것만 보인다.

### 빈 문서로 시작한다

`createKeelDocument` 의 씨앗 인자를 선택으로 바꾸고
`apps/web/src/document/seed.ts` 를 **지운다.** `SEED` 텍스트를 쓰는 곳은
`app/page.tsx` 한 곳뿐이다(`KEEL_SEED` 심볼은 별개이고 검사가 쓰므로 남긴다).

**여기서 공짜로 얻는 것이 있다.** 씨앗이 원격 업데이트로 도착하면 그 origin 은
제공자라 `trackedOrigins` 에 없다. 즉 **되돌리기가 씨앗을 지울 수 없다.** 지금
`KEEL_SEED` 심볼이 로컬에서 하던 일을 서버 구조가 그대로 해 준다.

### 내용이 있기 전에는 에디터를 세우지 않는다

빈 채로 띄우면 안 된다. 이론상으로는 `yCollab` 이 나중에 도착한 `Y.Text` 변경을
편집기에 반영하니 동작한다. 그런데 그 사이에 사람이 글자를 치면 **아직 도착하지
않은 씨앗과 섞인다.** 문서는 CRDT 라 깨지지 않지만 사람이 보기엔 글자가 엉뚱한
자리에 꽂힌다. 게다가 빈 문서는 진단 목록에 오류를 띄워, 켜자마자 빨간 줄을
보게 된다.

로컬 저장이 붙으면서 기다리는 규칙이 두 갈래가 된다.

1. **`local.whenSynced` 를 먼저 기다린다.** IndexedDB 라 빠르다.
2. 그러고도 문서가 **비어 있으면**(첫 방문) 원격 `sync` 를 마저 기다린다.
   비어 있지 **않으면 즉시 띄운다** — 서버 병합은 뒤에서 돈다.

두 번째 갈래가 체감 속도를 크게 바꾼다. 두 번째 방문부터는 네트워크를 안
기다린다.

### packages/contract 를 이제 채운다

`POST /d` 의 응답 타입과 오류 모양을 여기 둔다. 빈 껍데기로 있던 패키지의 원래
목적이고, web 과 api 가 같은 정의를 본다.

## 오류 처리

**원칙: 저장되지 않는 것을 저장된 것처럼 보이지 않게 한다.** 지금 화면은 저장이
없다는 것을 씨앗 주석으로 솔직히 드러내고 있다. 저장이 생기면 그 솔직함이
연결 상태 표시로 옮겨가야 한다.

| 실패 | 처리 |
|---|---|
| `/` 에서 `POST /d` 실패 | 서버 컴포넌트가 던지고 `error.tsx` 가 "서버에 연결할 수 없다". 새 문서를 못 만드는 것은 회복할 방법이 없다 |
| 없는 문서 id | 에디터 화면의 서버 컴포넌트가 `GET /d/:id` 로 먼저 확인하고 없으면 404 화면 |
| **문서 화면에서 서버에 못 붙음** | **화면을 막지 않는다.** 에디터를 띄우고 로컬 사본으로 돈다 |
| **유령 문서** — 서버엔 없는데 로컬엔 있다 | **로컬을 먼저 지우고**(`clearData()`) 404 화면 |
| 연결이 끊긴 채 편집 | 로컬에 쌓인다. 잃지 않는다. 안 보인다는 것만 표시 |
| IndexedDB 를 못 씀 | 조용히 로컬 저장 없이 돈다. 경고 문구를 원래의 강한 쪽으로 |
| 저장 실패 | 그 문서의 소켓을 전부 끊는다 |
| 복원 실패 | 접속을 거부한다 |
| DB 가 안 보임 | upgrade 를 `503` 으로 끊는다 — `404` 와 구분한다 |

**없는 문서를 404 로 내야 하는 이유.** 확인을 안 하면 ws 가 404 로 끊기고
사용자는 빈 에디터를 본다. "문서가 없다" 와 "문서가 비었다" 를 구분 못 하는
화면이다.

**그런데 못 붙었다고 화면을 막으면 안 된다.** 이 존재 확인은 서버 컴포넌트가
하므로, 서버가 죽어 있으면 확인 자체가 실패한다. 그때 오류 화면을 내면
**로컬에 사본을 들고 있는 사람이 오프라인에서 아무것도 못 한다** — 로컬
저장을 넣은 이유가 그 자리에서 통째로 사라진다.

그래서 세 갈래다. `404`(정말 없다)면 404 화면과 로컬 삭제, 못 붙었으면
에디터를 띄우고 클라이언트가 로컬을 보고 판단한다. 로컬에도 사본이 없을
때만 "서버에 연결할 수 없고 사본도 없다" 를 낸다. **"불러오는 중" 을 영원히
보여 주는 것이 제일 나쁜 결과다.**

**유령 문서가 이 판에서 제일 고약한 실패다.** 서버에서 문서가 사라졌는데
(삭제, DB 초기화) 로컬 IndexedDB 에는 남아 있는 경우다. 그대로 두면 사용자는
멀쩡해 보이는 문서를 열어 한참 고치는데, ws 는 404 로 계속 거부당하고 **그
작업은 영영 저장되지 않는다.** 끊긴 채 편집하는 것보다 나쁘다 — 저쪽은 언젠가
붙지만 이쪽은 영영 안 붙는다.

그래서 서버 컴포넌트의 존재 확인이 **로컬을 지울 권한까지 갖는다.** `404` 면
`clearData()` 를 먼저 부르고 404 화면을 낸다. `503`(DB 가 안 보임)에는 **지우지
않는다** — 그때 지우면 서버가 잠깐 아픈 사이에 사람의 오프라인 작업을 우리가
없앤다.

**끊긴 채 편집하는 것.** `y-websocket` 이 백오프로 재접속하고, 그 사이 편집은
`y-indexeddb` 가 브라우저에 쌓는다. 탭을 닫아도 남는다. 남은 문제는 유실이
아니라 **남들이 아직 못 본다**는 것뿐이라, 연결 상태 표시로 충분하다.

**IndexedDB 를 못 쓰는 경우.** 프라이빗 창이나 할당량 초과에서 던진다. 이때는
조용히 로컬 저장 없이 돌고, 연결 상태 문구를 원래의 강한 경고("지금 고치는 것은
저장되지 않는다")로 되돌린다. **에디터가 열리지 않는 것이 제일 나쁜 결과다.**

**저장 실패에 소켓을 끊는 이유.** `ydoc.on('update')` 에서 DB 쓰기가 실패하면 그
업데이트는 **이미 다른 접속자에게 중계된 뒤**다. 모두가 저장됐다고 믿는데 사실이
아니다. 소켓을 끊으면 클라이언트는 "연결 끊김" 으로 넘어가고, 그것은 사실이다 —
지금 고치는 것이 저장되지 않으니까. y-websocket 프로토콜에 앱 수준 메시지
통로가 없으니, 끊는 것이 우리가 가진 가장 정직한 신호다. 조용히 로그만 남기면
사람은 계속 작업하다 전부 잃는다.

**끊은 뒤 클라이언트는 곧바로 재접속을 시도한다.** 그대로 두면 된다 — DB 가
돌아왔으면 붙고, 아직이면 upgrade 시점의 존재 확인이 DB 를 때리므로 그쪽에서
막힌다. 즉 **재접속 고리가 저절로 건강 검사 노릇을 한다.** 따로 쿨다운을 두지
않는다. 다만 존재 확인이 DB 오류로 실패한 경우는 `404` 가 아니라 `503` 으로
끊는다 — "문서가 없다" 와 "지금은 못 본다" 는 다른 말이고, 404 로 내면
클라이언트가 없는 문서로 오해해 재접속을 포기한다.

**복원 실패에 접속을 거부하는 이유.** 업데이트 행 하나가 깨져 부분 복원된
문서를 내보내면 그 위의 편집이 갈라진 역사로 쌓인다. 부분 복원을 서비스하느니
거부한다.

## 검사

이 저장소의 방식을 그대로 — 순수 로직은 단위 검사로 두껍게, e2e 는 얇게.
그러려면 **결정을 순수 함수로 뽑아야 한다.**

| 층 | 무엇을 | 어떻게 |
|---|---|---|
| 단위 (I/O 없음) | 접기 판단 — 임계치 경계, 무엇을 접고 무엇을 남기는가 | `foldPlan(rows, threshold)` 를 순수 함수로 |
| 단위 (I/O 없음) | 복원 순서 — 스냅샷 + 꼬리 재생이 원본과 같은 상태를 내는가 | `Y.Doc` 둘을 손으로 붙여 비교 |
| 단위 (I/O 없음) | 씨앗 심기가 온전한 업데이트를 내는가 | 만든 업데이트를 빈 `Y.Doc` 에 적용해 원문과 견줌 |
| 통합 (실 DB) | bindState/writeState 왕복 — 만들기 → 고치기 → 재시작 → 복원 | compose 의 Postgres |
| 통합 (실 DB) | 스냅샷을 쓴 뒤 삭제 전에 죽은 경우 | 중복 적용이 무해한 것을 확인 |
| e2e | 새로고침해도 남는다 | Playwright |
| e2e | 두 브라우저가 서로 본다 | Playwright 컨텍스트 둘 |
| e2e | **끊긴 채 고친 것이 다시 붙을 때 올라간다** | `context.setOffline(true)` 로 끊고 고친 뒤 되붙임 |
| e2e | **유령 문서를 열면 404 이고 로컬이 지워진다** | 문서를 만들어 연 뒤 DB 에서 지우고 다시 연다 |

**두 브라우저 검사가 이번 조각의 핵심 증명이다.** README 첫 줄의 "실시간 협업"
이 실제로 도는지를 처음으로 기계가 확인하는 자리다.

**"스냅샷 먼저, 삭제 나중" 을 검사가 들고 있게 한다.** 스냅샷을 쓴 뒤 삭제 전에
죽은 상황을 흉내 내고, 다시 복원했을 때 문서가 온전한지 본다. 그 순서를 그렇게
정한 이유가 글이 아니라 검사로 남는다.

## 이 판에서 같이 고칠 것

- **e2e 가 Postgres 와 api 를 필요로 하게 된다.** `playwright.config.ts` 의
  `webServer` 를 배열로 늘려 api 도 띄우고, Postgres 는 `compose.yaml` 로
  올린다. 기존 검사 5 개는 흐름이 유지된다 — `/` 가 새 문서를 만들어 보내주므로
  `goto('/')` 는 여전히 씨앗이 선 화면에 닿는다. 다만 매 실행마다 새 문서가
  생긴다.
- **CI 의 `verify.yml` 에 `services: postgres:` 를 붙인다.** GitHub Actions 가
  서비스 컨테이너를 지원하니 도커 컴포즈를 CI 에서 직접 돌릴 필요는 없다.
- **`createKeelDocument` 의 씨앗 인자를 선택으로 바꾼다.**

## 범위 밖

- 구글 로그인·소유권·권한 (다음 조각)
- 프레즌스와 사람별 커서 색 (`PaintOptions.selection` 확장이 선행 과제)
- 오프라인의 나머지 — 충돌 UX, 백오프 조정, 상세 동기화 상태. **로컬에 안
  잃게 하는 것만** 이 판에 들어온다
- R2 스냅샷 — Postgres `bytea` 로 시작한다
- 인스턴스 2 대 이상 (Redis pub/sub 팬아웃)
- 문서 목록 화면·삭제·공유 UI
- 배포 대상 선정과 배포 파이프라인

## 앞날에 걸릴 것

- **인스턴스를 늘리는 순간** 같은 문서가 두 메모리에 뜬다. `y-redis` 가 정확히
  그 문제를 푸는 물건이라, 그때 자체 팬아웃을 만들기 전에 먼저 본다.
- **업데이트 로그가 길어지면** 접기가 잦아진다. 200 은 재 보지 않고 고른 수다.
  실제 편집 패턴에서 접기 비용과 복원 비용을 재서 고친다.
- **버전 스냅샷 화면**은 이 로그 위에 선다. 그때 `DocUpdate` 에 사람 id 가
  필요해지는데, 인증이 먼저 와야 채울 값이 생긴다.
- **로컬 사본이 기기마다 따로 쌓인다.** 노트북에서 오프라인으로 고친 것은 그
  노트북이 다시 붙기 전까지 휴대폰에 안 보인다. 고칠 방법이 없고 고칠 필요도
  없지만, 사람이 "저장했는데 없다" 고 말할 때 여기를 먼저 의심해야 한다.
- **로컬 사본을 언제 비울 것인가.** 지금은 유령 문서일 때만 지운다. 문서를 많이
  열면 IndexedDB 가 계속 쌓이는데, 할당량에 닿기 전까지는 문제가 아니다. 문서
  목록 화면이 생길 때 같이 본다.

## 알고 있는 검사 구멍

`bindState` 가 스냅샷과 꼬리를 한 트랜잭션(`RepeatableRead`)으로 읽는 것은
**데이터 무결성 불변식**이다. 나눠 읽으면 그 사이에 접기가 착지했을 때
스냅샷은 `null` 로, 꼬리는 새 `throughSeq` 이후만 읽혀 **그 구간이 통째로 빈
문서**를 조용히 내준다. 로그가 200 을 넘긴 문서를 새로고침하면 닿는다.

그런데 **프로덕션 `bindState` 를 실제 동시 접기와 맞붙이는 검사가 없다.**
두 검사가 나눠 지킨다 — 하나는 `$transaction` 이 `RepeatableRead` 로 불리는
것을 스파이로 고정하고(주어는 맞되 술어가 약하다), 하나는 같은 트랜잭션
모양에 진짜 `CompactionService.fold` 를 붙여 Repeatable Read 가 커밋된 접기를
실제로 가린다는 것을 보인다(술어는 맞되 주어가 복제본이다).

**따라서 `$transaction` 호출은 남긴 채 두 읽기 중 하나를 밖으로 빼는 리팩터링은
검사를 전부 통과하면서 버그를 되살린다.** 메서드를 건드릴 때 이 문단을 볼 것.

막는 방법이 둘 있고 둘 다 시도되지 않았다. 싼 쪽은 스파이가 잡은 콜백을
기록용 프록시 `tx` 로 다시 불러 **두 읽기가 모두 그 프록시에서 나갔는지**를
단언하는 것 — 모양이 아니라 성질을 검사하게 된다. 비싼 쪽은 Prisma 클라이언트
확장(`$extends`)을 주입 지점으로 쓰는 것인데, 확장은 대화형 트랜잭션 클라이언트
에서도 도므로(원숭이 패치와 달리) 진짜 `bindState` 안에서 창을 열 수 있다.
